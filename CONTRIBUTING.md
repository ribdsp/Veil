# Contributing

Thanks for looking. Veil started as a hackathon project, so the codebase is small and the conventions
are few — but the few there are hold up the project's central claim, and this document is where
they're written down.

---

## Getting set up

```bash
git clone https://github.com/ribdsp/Veil.git
cd Veil/veil && npm install && npm run dev      # the app → localhost:3000

cd ../fixtures && node generate.mjs --rows 5000 --messy   # synthetic data to work against
```

To exercise the tool surface you need WebMCP available in the browser. Three options, in descending
order of fidelity:

1. **Chrome 149+ or Edge 150+ with an origin trial token** for your origin. Closest to what real users
   get, and the only setup where `exposedTo` actually gates anything.
2. **The WebMCP polyfill** (`veil/src/lib/webmcp/polyfill.ts`), which loads automatically in
   development. Good enough for building; not good enough for judging whether a schema is legible to a
   model.
3. **The `webmcp-tools` browser extension**, which gives you an inspector over the registered tools.
   Use this to call tools by hand.

You don't need a real agent for most work. You do need one before claiming a tool works — see
[Testing a tool](#testing-a-tool).

### `npm audit` is not clean, on purpose

Two advisories remain, both against the PostCSS that Next 15 pins internally, and both fixable only by
upgrading to Next 16. We are staying on 15 for now: the advisories are build-time path traversal and
CSS-stringifier XSS, the only stylesheet Next processes here is our own, and no untrusted CSS reaches
the build. Upgrading a framework major is a change worth making deliberately rather than to make a
number go to zero.

If you upgrade it, say so in the PR and check `next.config.mjs` first — the WebMCP origin trial token is
served as an HTTP header from there, and that is the part most likely to move.

Anything that ships to the browser is a different matter. A runtime advisory in `react`, `next`,
`zustand` or `papaparse` is a real finding here, because this app's entire claim is that the file never
leaves the tab.

## Four rules that aren't negotiable

These come from the [threat model](docs/threat-model.md). A PR that breaks one will be rejected even
if everything else about it is good.

### 1. No tool may read a cell

`lib/data` does not export the raw cell accessor. Tools ask the guard a *question* — a structured
predicate or aggregation — and the guard answers or refuses. This is the whole architecture, not a
convention.

`guard/no-leak.test.ts` greps every file in `lib/webmcp/tools/` and fails the build if one reaches
past the guard. If you need data a tool cannot currently get, the fix is a new guarded query type with
its own suppression rule, never a direct read. `request_reveal` is the single exception, and it is an
exception because a human clicks.

### 2. Nothing from the model is ever executed

No `eval`, no `new Function`, no dynamic `import()` of a model-supplied string, no
`setTimeout("string")`, **and no regex built from a model-supplied string**. Predicates, transforms and
format names are closed unions that a switch statement interprets.

The regex clause is the one people push back on, so: a pattern from a model is a denial-of-service risk
through catastrophic backtracking, and worse, it is a high-bandwidth side channel. `^0812(\d)`, then
`^08121(\d)`, and so on — ten legal, k-safe counts later the agent has extracted a whole phone number
without ever calling a reveal. Named formats cost flexibility and buy the boundary being real.

There is a test that greps the source for `eval(` and `new Function` and fails the build. If you find
yourself wanting to suppress it, that's the signal to stop and open an issue instead.

### 3. Every tool response has a budget, and every refusal is reported

Pattern buckets: 8. Aggregate groups: 25, then `__other__`. Duplicate pairs: 50. Issue rows: 100.
Masked exemplars: 10. Queries per column: 12.

New tools need a budget too. Pick one, enforce it in the response, set a `truncated` flag, and tell the
agent what to do about it (`"narrow the scope"`) rather than only reporting that something was cut.
Agents act on instructions much more reliably than on observations.

Suppressions are subject to the same rule from the other direction: a suppressed answer must say it was
suppressed and why. An agent that receives a silent zero draws conclusions from it — that is how you
get a confident report about a dataset the agent was never allowed to see.

### 4. No real data in this repository, ever

Every CSV in `veil/public/samples/` is synthetic, generated by `fixtures/`. A row of real data contains
whatever a real person told somebody: their name, their number, their salary, their diagnosis.

`.gitignore` blocks `*.csv`, `*.xlsx` and `*.xls` with a single allow-list for the samples directory,
but the rule matters more than the mechanism. It applies to bug reports too: if your own spreadsheet
triggers a bug, reproduce it with a generated file and attach that. If you cannot reproduce it
synthetically, describe the shape of the data in words — column types, row counts, what the values look
like — and we'll build a fixture together.

## Code conventions

- **TypeScript strict.** No `any` in `lib/`. If a type is genuinely unknown, `unknown` plus a
  narrowing function.
- **JSON keys are camelCase**, in tool responses and everywhere else.
- **File names are kebab-case.** `k-anonymity.ts`, not `kAnonymity.ts`.
- **`lib/` is pure.** `lib/data`, `lib/guard`, `lib/dedupe` and `lib/transform` take data and return
  data. They don't import React, don't touch the store, and don't know WebMCP exists. This is what
  makes them testable without a browser — please don't erode it for convenience.
- **Every state mutation goes through an action, and every action carries `author`.** No direct
  `setState` from components. The journal's correctness depends entirely on this, including for code
  written by people who never read this file.
- **Actions return new objects.** Undo needs previous states intact.
- **Small files.** 200–400 lines is normal; past 800, split.

## Testing policy

Deliberately uneven, and worth explaining rather than defending.

**Tested thoroughly:**

| Module | Why |
|---|---|
| `guard/k-anonymity` | an off-by-one here publishes a group of four people |
| `guard/query-budget` | the differencing defence; an unenforced budget is no defence |
| `guard/predicate` | it's the security boundary |
| `dedupe/similarity` | a wrong score merges two different people's records |
| `transform/apply-transform` | it edits the user's data, and undo has to be exact |
| the no-`eval` and no-leak greps | prevent quiet regression under time pressure |

**Not covered by automated tests:** UI components, the file-picker flow, end-to-end runs with a live
agent.

The reasoning: bugs in the modules above fail *invisibly* — you get a plausible answer that's wrong, or
a leak nobody notices. Bugs in the UI announce themselves within five seconds of opening the page. The
test budget goes where failures hide, not where they're loud.

```bash
cd veil && npm test
```

If you add anything to `lib/guard`, `lib/dedupe` or `lib/transform`, it needs tests. UI is fine
without.

**A privacy test is not allowed to be relaxed to pass.** If `k-anonymity.test.ts` fails, the guard is
wrong or the specification changed; those are the only two options, and the second one is a discussion
before it is a diff.

## Testing a tool

A tool that works when you call it from your own code can still be unusable, because the failure mode
is a schema a model consistently misreads. Before saying a tool works:

1. Call it from the `webmcp-tools` inspector with arguments you type by hand.
2. Call it from a real agent, with a task phrased the way a user would phrase it — *"tidy up this
   customer list"* — not with arguments you already know are correct.
3. Check that failures come back as **readable tool errors**, not thrown exceptions. Good:
   `Unknown format 'phone_id'. Supported: e164, local_id_phone, digits_only, ...`
   An agent given that sentence corrects itself on the next call.
4. Check the suppression path specifically. Craft a predicate that matches three rows and confirm the
   agent is told *why* it got nothing, and what it might ask instead.

Tool `description` fields are part of the interface. A tool whose description doesn't explain *when* to
use it will be used at the wrong moment. `request_reveal` in particular has to state that reveals are
expensive, logged, and refusable, or models reach for it as a general-purpose escape from uncertainty —
which is precisely the behaviour this project exists to make unnecessary.

## UI conventions

Veil is an instrument for someone doing careful work with a file that matters: **dense, quiet,
scannable.** No decorative gradients, no oversized rounded cards, no marketing voice in an ops tool.

Three conventions are semantic rather than aesthetic, and code depends on them:

- **The veil hatch means "the agent has not been shown this."** It is a hatch and not a blur, because a
  blurred value looks recoverable and invites squinting. Never use it decoratively.
- **`revealed` red is reserved for a granted reveal.** Nothing else in the app may use it. It is the
  most expensive event in the product and it should be visible from across the room.
- **Author colour is `human` or `agent`, everywhere, consistently.** A user should be able to answer
  "did I do that or did it?" without reading a label.

Empty, loading, and error states are all three required, not just the one you happened to hit while
developing. Suppression is a fourth state and it needs its own treatment: it is *informative*, not an
error, and styling it like a failure teaches people that privacy is the exception.

## Pull requests

- Branch off `main`, which stays deployable.
- Small and frequent beats large and complete.
- PRs touching `lib/guard` need a second reader, and so do new tools. `components/` doesn't.
- Commit messages: `<type>: <description>` with types `feat`, `fix`, `refactor`, `docs`, `test`,
  `chore`, `perf`, `ci`.

## Adding a tool

The checklist, in order:

1. A pure function in `lib/` that does the actual work, with tests if it's in `guard`/`dedupe`/
   `transform`.
2. A guarded query — the function must reach data *through* `lib/guard`, never around it.
3. A thin wrapper in `lib/webmcp/tools/<name>.ts`.
4. A response budget and an explicit suppression rule. Answer "what does this return when the honest
   answer describes two people?" before writing the happy path.
5. A JSON Schema with a `description` on the tool **and on each non-obvious field**, plus an example.
6. Readable errors for every rejection path.
7. A decision about exposure: does this belong in the read-only set, or in the trusted set behind
   `exposedTo`? Anything that can uncover a value, mutate data, or end the run is trusted.
8. An entry in [docs/tools.md](docs/tools.md) — the contract is documentation, not just code.
9. Tested from the inspector *and* from a real agent, including the suppression path.
