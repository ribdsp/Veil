# Working in this repository

Notes for whoever — or whatever — writes code here. If you are an AI coding agent, read this file
before your first edit, then `CONTRIBUTING.md`.

## Read in this order

1. **`CONTRIBUTING.md`** — the four non-negotiable rules, code conventions, testing policy
2. **`docs/architecture.md`** — how the pieces fit, and why the guard sits between tools and data
3. **`docs/tools.md`** — the 14-tool contract
4. **`docs/privacy-guard.md`** — required reading before you touch `lib/guard`

## The one thing this codebase is about

No tool may read a cell. Tools ask `lib/guard` a structured question and receive an answer or a
refusal; the raw cell accessor is module-private to `lib/data` and there is a test that greps every
tool file to keep it that way.

If a task seems to require reading a value directly, the intended answer is almost always a new
*guarded query* with its own suppression rule — not a direct read, and not an export added to
`lib/data` "just for this". Should you conclude the guard genuinely has to be bypassed, say so in your
final message and stop. That is a design decision, not an implementation detail.

## One area per change

The codebase is split **by folder, not by feature**, so that concurrent work rarely lands on the same
lines. Two consequences:

- **Keep a change inside the area you were asked to work on.** If the fix you need lives elsewhere,
  **say so in your final message instead of making it.** A patch that helpfully repairs a neighbouring
  module hands its maintainer a conflict to resolve blind, in code they didn't write.
- **`src/types/domain.ts` is a frozen contract.** Every other module depends on it, which makes adding
  a type there a conversation rather than a commit.

Who holds which area isn't listed here on purpose: it changes, and a stale ownership table is worse
than none. Whoever asked you to make this change will tell you your scope.

## `TODO(name), Day n:` markers are assignments

Every stub names the person who owned it and the day it was due during the original build. Implement
the ones you were asked to implement; leaving the rest alone is correct behaviour, not incompleteness.
Deleting a marker while implementing around it destroys the only record of who owes what.

## Some tests are red on purpose

`k-anonymity`, `query-budget`, `predicate`, `similarity` and `apply-transform` ship with failing tests.
They were written first, as specifications. **Never** make them pass by weakening an assertion, adding
`.skip`, or deleting a case: that converts a specification into a lie, silently, and here the lie is
about whether a real person can be identified from the output.

Two tests are security boundaries rather than lint rules, and both work by grepping the source:

- `no-eval.test.ts` fails if `eval(` or `new Function` appears anywhere in `src/`.
- `guard/no-leak.test.ts` fails if any file in `lib/webmcp/tools/` reaches past the guard to raw data.

## Never put real data in this repository

Only synthetic CSVs generated by `fixtures/`. `.gitignore` blocks `*.csv`, `*.xlsx` and `*.xls` with a
single allow-list for `veil/public/samples/`. If you are asked to add a test dataset, generate one; do
not adapt something you found on the machine, and do not paste rows of anything real into a test file
as a fixture literal.

## Verify instead of asserting

Dependencies may not be installed in a fresh clone, so nothing has typechecked yet:

```bash
cd veil && npm install && npx tsc --noEmit && npm test
```

Run that before claiming a change compiles. For tools specifically, "it works" means called from the
`webmcp-tools` inspector *and* from a real agent — see `CONTRIBUTING.md` § Testing a tool. It also
means you exercised the refusal path: a tool whose happy path is correct and whose suppression path
returns a bare `0` is a leak with good test coverage.
